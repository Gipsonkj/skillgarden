# Postgres schema design

> Distilled from: postgresql-table-design (wshobson/agents, MIT), supabase-postgres-best-practices (supabase/agent-skills, MIT), postgres-patterns (affaan-m/ECC, MIT), neon-postgres (neondatabase/agent-skills, Apache-2.0); time-zone section also from the Book of Revenue write-up on AT TIME ZONE (bookofrevenue.com).

Use this when creating tables, choosing types and keys, adding constraints, or writing migrations for Postgres (including Supabase and Neon).

## 1. Types

| Data | Use | Avoid |
|---|---|---|
| Internal primary key | `bigint generated always as identity` | `serial` (legacy), `int` (overflows at 2.1 billion) |
| ID exposed in URLs or generated by clients / distributed writers | UUIDv7 (`uuid` column, time-ordered) or a separate random public id | random UUIDv4 as the clustered PK on hot tables (index fragmentation) |
| Text | `text` + `CHECK (length(x) <= n)` when a limit matters | `varchar(n)` as a habit, `char(n)` |
| Timestamps | `timestamptz` (see section 7) | `timestamp` without time zone |
| Money | `numeric(12,2)` or integer minor units (cents) | `float`, `real`, `money` |
| Booleans | `boolean NOT NULL DEFAULT false` | nullable booleans (three states) |
| Enumerations | `text` + `CHECK (status IN (...))` or a lookup table | Postgres `enum` if values change often (adding is easy, removing is not) |
| Semi-structured | `jsonb` (with GIN index if queried) | `json`, or jsonb for data you filter and join on constantly |
| IP addresses | `inet` / `cidr` | text |

Decision rule for keys: internal joins use the bigint; anything a user can see or guess uses UUIDv7 or a random public id. This keeps indexes compact while avoiding enumerable public ids.

## 2. Constraints are features

- `NOT NULL` on every column that must have a value; nullable is the exception you justify.
- Foreign keys with explicit `ON DELETE` (`CASCADE` for owned children, `RESTRICT` for references, `SET NULL` rarely).
- `UNIQUE` for natural keys (email per tenant: `UNIQUE (tenant_id, lower(email))` via a unique index on the expression).
- `CHECK` constraints for ranges and states (`CHECK (quantity > 0)`).
- `created_at timestamptz NOT NULL DEFAULT now()`, `updated_at` maintained by a trigger or the app.

## 3. Indexes you need from day one

- **Every foreign key column gets an index.** Postgres does not create them; missing ones make joins and cascading deletes slow.
- Columns in frequent `WHERE`, `ORDER BY` and join conditions.
- Details on composite, partial, covering, GIN and BRIN indexes: see query-performance.md.

## 4. Multi-tenancy

| Model | When | Notes |
|---|---|---|
| `tenant_id` column on every table | Default for SaaS | Composite indexes start with `tenant_id`; enforce with RLS or a scoped query layer |
| Schema per tenant | Few large tenants with custom needs | Migrations multiply |
| Database per tenant | Strict isolation or data residency | Neon/branching makes this cheaper; pooling multiplies |

## 5. Normalization and denormalization

- Start normalized (3NF). Denormalize only for a measured read hotspot, and record how the copy stays in sync (trigger, materialized view refresh, application write).
- Materialized views for expensive aggregates; refresh `CONCURRENTLY` (needs a unique index).
- Partition only very large, time-series tables (hundreds of millions of rows) by range on the time column.

## 6. Migrations

- One migration per change, forward-only in production, checked into git, applied by a tool (Prisma Migrate, Drizzle, Supabase CLI, sqitch, Flyway).
- Safe online changes:
  - Add nullable column, backfill in batches, then add `NOT NULL` (on large tables add a `CHECK ... NOT VALID`, `VALIDATE` later).
  - `CREATE INDEX CONCURRENTLY` (not inside a transaction).
  - Rename via add new / dual write / backfill / switch reads / drop old.
- Set `lock_timeout` (for example `'5s'`) in migrations so a blocked DDL fails instead of queueing all traffic behind it.
- Run migrations over a **direct** (non-pooled) connection.

## 7. Time zones

- Store instants as `timestamptz`. It holds a UTC instant; the session `TimeZone` setting only changes how values are parsed and displayed.
- `AT TIME ZONE` flips the type. On a `timestamptz` it returns a plain `timestamp` (wall-clock time, zone dropped); on a plain `timestamp` it returns a `timestamptz`. So `created_at at time zone 'UTC'` is no longer an instant, and comparing it with a `timestamptz` casts it using the session zone: right on a UTC server, silently wrong on a laptop set to another zone.
- Do date arithmetic in a named zone, then flip back so the result is a `timestamptz` again: `(created_at at time zone 'UTC' + interval '1 month') at time zone 'UTC'`.
- To bucket by day in a zone, use `date_trunc('day', created_at, 'UTC')` (Postgres 12+, returns `timestamptz`). For display-only grouping cast to a date: `(created_at at time zone 'Asia/Kolkata')::date`.
- Use IANA names (`Europe/Berlin`), not fixed offsets or abbreviations, so daylight saving is right. For future local events (a 9:00 meeting), store the local time plus the zone name, not only the UTC instant.
- Prove it: run the query under `set timezone = 'America/Los_Angeles'` and again under `'UTC'`; the results must match.

## 8. Example

```sql
create table orders (
  id          bigint generated always as identity primary key,
  public_id   uuid not null default gen_random_uuid() unique, -- or a UUIDv7 generator
  tenant_id   bigint not null references tenants(id) on delete cascade,
  customer_id bigint not null references customers(id) on delete restrict,
  status      text   not null default 'pending'
              check (status in ('pending','paid','shipped','cancelled')),
  total_cents bigint not null check (total_cents >= 0),
  created_at  timestamptz not null default now()
);
create index on orders (tenant_id, created_at desc);
create index on orders (customer_id);
```
